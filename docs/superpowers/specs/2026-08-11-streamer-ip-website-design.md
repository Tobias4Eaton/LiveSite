# 實況主 IP 獨立網站 — 設計文件

日期：2026-08-11
狀態：已與站主確認方向（方案 B）

## 目標

建立一個專屬於實況主本人的 IP 網站：集中呈現 Twitch 嵌入直播、YouTube 影片、自我介紹、所有社群連結與最新資訊，並支援聊天室機器人的指令大全展示與即時小遊戲顯示（網站頁面 + OBS 覆蓋層 + 網站直接參與）。

## 範圍與優先序

**最優先：網站設計與建置。** 機器人（跑在站主電腦上、開台時運行）已有現行版本，將於稍後提供；本文件對機器人只定義「介接契約」（資料表結構與即時頻道格式），不設計機器人內部。網站建置完成後，任何符合契約的機器人皆可直接接上。

實作階段：

1. **IP 門面站**：首頁、自介、影片牆、社群連結、最新資訊（可先上線）
2. **指令大全頁**：讀取 `commands` 資料表（機器人日後自動同步）
3. **即時遊戲顯示**：遊戲頁 + OBS 覆蓋層，訂閱 Realtime 頻道（機器人接上前顯示離線狀態）
4. **網站互動**：Twitch 登入、觀眾在網頁上直接參與遊戲（寫入 `game_actions`）

## 架構總覽（方案 B）

Monorepo（pnpm workspaces），全 TypeScript：

```
MySite/
├── apps/web        ← Astro 網站，部署至 Cloudflare Pages（免費）
├── apps/bot        ← 機器人（待站主提供現行版本後再規劃）
└── packages/shared ← 共用型別：遊戲狀態、即時頻道訊息格式
```

- **前端**：Astro，預設純靜態輸出；互動區塊（遊戲頁、即時顯示）用 React 島嶼。
- **雲端骨幹**：Supabase 免費層 — Postgres（指令、公告、遊戲紀錄）、Realtime（即時廣播）、Auth（Twitch OAuth 登入）。
- **機器人**：跑在站主電腦上，開台時運行；透過 service key 讀寫 Supabase。
- **月費**：$0。可選自訂網域約 US$10/年。

資料流：

- 觀眾瀏覽器 → Cloudflare Pages（靜態內容）＋ Supabase（動態資料、即時訂閱）
- 機器人 ⇄ Twitch 聊天室；機器人 ⇄ Supabase（廣播狀態、同步指令、收網站玩家操作）
- OBS 瀏覽器來源 → 網站 `/overlay` 頁（與遊戲頁共用元件與資料）

## 資料模型（Supabase Postgres）

| 資料表 | 用途 | 寫入者 |
|---|---|---|
| `commands` | 指令大全：名稱、說明、用法、分類、冷卻、啟用狀態 | 機器人啟動時 upsert 同步 |
| `news` | 最新資訊/公告：標題、內文、發布時間、置頂 | 站主（Supabase Studio 後台直接編輯） |
| `game_sessions` | 每場遊戲紀錄：類型、起訖時間、最終狀態(jsonb) | 機器人 |
| `player_scores` | 觀眾累積積分/排行榜 | 機器人 |
| `game_actions` | 網站玩家操作（下注、猜拳…） | 登入觀眾（RLS：僅能寫入自己的列） |

原則：

- 指令大全**不手動維護**——機器人啟動時把程式內定義的指令清單 upsert 至 `commands`，網站自動更新。
- 自介、社群連結等幾乎不變的內容直接寫在網站程式碼中，不進資料庫（YAGNI）。
- 所有資料表開啟 RLS；公開資料（commands、news、scores、sessions）僅開放讀取，`game_actions` 僅允許登入者寫入自己的列。

## 即時資料流（介接契約核心)

**顯示方向**：機器人透過 Supabase Realtime 頻道（`game:live`）廣播遊戲狀態快照與事件，節流至每秒數次。網站遊戲頁與 OBS 覆蓋層訂閱同一頻道，共用同一套 React 元件。

**參與方向**（兩條輸入路徑匯入同一個遊戲引擎）：

- 聊天室：觀眾輸入 `!指令` → 機器人直接處理。
- 網站：觀眾以 Twitch 帳號登入（Supabase Auth）→ 操作寫入 `game_actions` → 機器人訂閱該表 INSERT 事件，視為與聊天指令等價的輸入。

遊戲邏輯只存在機器人內一份；網站永遠只是「顯示器＋輸入裝置」。訊息格式（狀態快照、事件、操作）的 TypeScript 型別定義於 `packages/shared`，作為網站與機器人之間的正式契約。

**在線判定**：機器人加入 Realtime 頻道時登記 presence；機器人離線（沒開台）時 presence 自動消失，網站顯示「目前離線」＋歷史排行榜，不需輪詢。

## 頁面結構

| 路徑 | 內容 |
|---|---|
| `/` | 主視覺、Twitch 嵌入播放器、社群連結、最新消息摘要 |
| `/about` | 自我介紹 |
| `/videos` | YouTube 影片牆（官方 RSS feed 抓最新影片，免 API 金鑰） |
| `/commands` | 指令大全：搜尋、分類（讀 `commands` 表） |
| `/game` | 即時遊戲頁：現場狀態、排行榜；登入後可參與 |
| `/overlay` | OBS 透明背景覆蓋層；以網址參數選擇顯示元件 |

公告發布流程：站主於 Supabase Studio 新增 `news` 列，網站即時反映，無需重新部署。

## 錯誤處理與韌性

- **機器人離線**：遊戲頁/覆蓋層顯示離線狀態與歷史資料（presence 判定）。
- **Supabase 免費層閒置暫停**：GitHub Actions 每週排程 ping 一次保持活躍。
- **觀眾端斷線**：supabase-js 自動重連；覆蓋層顯示小型連線狀態指示。
- **廣播節流**：機器人端限制廣播頻率（契約中註明上限），避免撞免費層額度。

## 測試策略

- `packages/shared`：訊息格式驗證與（未來的）遊戲邏輯以純函式撰寫，Vitest 單元測試為主要投資。
- 網站：建置檢查（`astro check` + build）為主；互動元件挑關鍵者寫元件測試，不過度測試。
- 機器人：待現行版本提供後另行規劃。

## 明確不做（YAGNI）

- 不自建後台管理介面（用 Supabase Studio）。
- 不做網站端遊戲邏輯（只顯示與輸入）。
- 社群連結/自介不進資料庫。
- 不使用 YouTube Data API（RSS 已足夠）。
